`InterestRateConfigServiceImplTest` **并没有真正往数据库里插入数据**。这是 Mockito 单元测试的常见做法：把依赖 Mock 掉，只验证业务逻辑是否按预期调用。

## 实际发生了什么

测试里用的是 Mock，不是真实 Mapper：

```java
@Mock
private InterestRateConfigMapper interestRateConfigMapper;  // 假对象

@InjectMocks
private InterestRateConfigServiceImpl service;              // 被测 Service
```

例如 T1「正常新建」里：

```java
when(interestRateConfigMapper.countOverlap(...)).thenReturn(0);   // 假装：没有重叠
when(interestRateConfigMapper.insert(any())).thenReturn(1);       // 假装：insert 成功

service.addOrUpdate(req);   // 调用真实 Service 逻辑

verify(interestRateConfigMapper).insert(captor.capture());      // 验证：确实调用了 insert
// 检查 captor 里 entity 的字段是否正确
```

流程可以概括为：

```
真实代码路径          实际执行
─────────────────────────────────────
validateRequest()    ✅ 真实执行（校验逻辑）
validateNoOverlap()  ✅ 真实执行 → 调用 Mock 的 countOverlap
insert(entity)       ❌ 不连库 → 只调用 Mock 的 insert，返回预设的 1
```

所以：

- **没有** Spring 容器
- **没有** 数据源 / MyBatis 连接
- **没有** 真实 SQL
- 只是在内存里跑 Service 代码，并断言「该调用的方法有没有被调用、参数对不对」

## 和「真插入」的区别

| | 单元测试（当前） | 集成测试 / 启动 Spring Boot |
|---|---|---|
| 数据库 | 不连接 | 连接真实库 |
| Mapper | Mock | 真实 Bean |
| 验证什么 | 业务逻辑 + 方法调用 | 端到端 + 库里真有数据 |
| 速度 | 快（毫秒级） | 慢（要起容器、连库） |

## 为什么要这样写

需求文档里的 T1–T13 主要验证的是：

- 重叠校验会不会抛 `BizException`
- 利率/日期/计息天数校验
- 新建时 `insert` 是否被调用、字段是否正确
- 编辑时是否 `updateById`、是否排除自身做重叠检查

这些都可以在 **不连库** 的情况下测完，所以不需要启动 Spring Boot。

## 如果想「真插入数据库」

需要另写 **集成测试**，例如：

```java
@RunWith(SpringRunner.class)
@SpringBootTest
@Transactional  // 测完回滚，避免污染数据
public class InterestRateConfigServiceIntegrationTest {
    @Autowired
    private InterestRateConfigService service;
    // 这里 addOrUpdate 才会真正写库
}
```

那种测试才需要启动 Spring Boot，并配置可用的测试库。

## 单元测试 vs 集成测试

### 一句话

- **单元测试**：只测「这一块代码」本身，依赖全部 Mock，**不启动 Spring、不连库**。
- **集成测试**：测「多块组件拼在一起」是否正常，**启动 Spring、连真实库/Redis 等**，走完整链路。

---

### 对比表

| 维度 | 单元测试 | 集成测试 |
|------|----------|----------|
| **测什么** | 单个类/方法的逻辑 | 多个模块协作（Controller → Service → Mapper → DB） |
| **依赖** | Mock 假对象（`@Mock`） | 真实 Bean（`@Autowired`） |
| **Spring Boot** | 不需要 | 通常需要 `@SpringBootTest` |
| **数据库** | 不连接 | 连接测试库，可能真 insert/update |
| **速度** | 很快（毫秒～秒） | 较慢（起容器、连库） |
| **定位问题** | 逻辑 bug（校验、分支） | 配置、SQL、事务、接口契约 |
| **稳定性** | 高，不依赖环境 | 依赖库、网络、数据状态 |

### 测试金字塔（常见做法）

```
        /\
       /  \     E2E / 手工 .http 联调（最少）
      /────\
     / 集成 \    关键接口 + 真实库（适量）
    /────────\
   /  单元测试 \  Service/Controller 逻辑（最多）
  /────────────\
```

- **单元测试**：数量多、跑得快，日常改代码就跑。
- **集成测试**：覆盖关键路径（如重叠 SQL、CRUD 真写库）。
- **E2E / `.http`**：联调、验收，不替代自动化。

---

### 怎么选

| 场景 | 更合适 |
|------|--------|
| 校验规则、分支、异常文案 | 单元测试 |
| SQL 是否正确、索引、闭区间重叠 | 集成测试 |
| 前端联调、菜单权限 | 启动应用 + `.http` / Postman |
| CI 每次提交快速反馈 | 单元测试为主 |

---

### 和「要不要启动 Spring Boot」的关系

| 测试类型 | 是否启动 Spring Boot |
|----------|----------------------|
| Service 单元测试（Mock Mapper） | **否** |
| Controller 单元测试（MockMvc + Mock Service） | **否** |
| 集成测试（`@SpringBootTest` + 真实 Mapper） | **是** |
| `.http` 手工接口测试 | **是**（应用必须跑着） |

你们当前的 `InterestRateConfigServiceImplTest` / `InterestRateConfigControllerTest` 都属于**单元测试**，所以不需要启动 Spring Boot，也不会真的插入数据库。若要验证「重叠 SQL 在库里是否生效」，需要再写集成测试或本地起服务后用 `.http` 测。

| **准备** | Arrange | 造输入、Mock 返回值 | `baseReq`、`when(...)` |
| **执行** | Act | 调用被测方法 | `service.addOrUpdate(req)` |
| **断言** | Assert | 检查结果是否符合预期 | `assertNotNull`、`verify`、`assertEquals` |

读任何测试时，先找这三块：**准备了什么 → 调了谁 → 期望什么**。

---

## 2. 类上的注解：测试怎么跑起来

```java
@RunWith(MockitoJUnitRunner.class)   // 告诉 JUnit：用 Mockito 创建 @Mock / @InjectMocks
public class InterestRateConfigServiceImplTest {

    @Mock
    private InterestRateConfigMapper interestRateConfigMapper;  // 假 Mapper

    @InjectMocks
    private InterestRateConfigServiceImpl service;              // 真 Service，依赖注入 Mock

    @Before
    public void setUpLangResources() { ... }  // 每个 @Test 运行前都会先跑一遍

    @Test
    public void addOrUpdate_create_success() { ... }  // 一个独立测试用例
}
```

| 注解 | 含义 |
|------|------|
| `@RunWith(MockitoJUnitRunner.class)` | 启用 Mockito，自动创建 Mock 对象 |
| `@Mock` | **假对象**：有方法名，但内部不连库，行为由 `when` 定义 |
| `@InjectMocks` | **被测对象**：把上面的 `@Mock` 塞进这个类的字段里 |
| `@Before` | 每个测试方法**之前**执行的公共准备 |
| `@Test` | 标记这是一个测试；JUnit 会单独运行它 |
| `@Test(expected = BizException.class)` | 期望执行时**必须抛出**指定异常，否则测试失败 |

## 3. Mockito：`when` ——「假如调用 X，就返回 Y」

```java
when(interestRateConfigMapper.countOverlap(...)).thenReturn(0);
when(interestRateConfigMapper.insert(any())).thenReturn(1);
```

含义：**当** Service 里调用 `countOverlap` 时，**不要真查库**，直接假装返回 `0`（表示没有重叠）。

可以读成自然语言：

> 假如有人调 `countOverlap(...)`，你就回答：0 条重叠。

`when` 里常见的参数匹配：

| 写法 | 含义 |
|------|------|
| `eq(1001L)` | 参数必须**等于** 1001 |
| `any()` | 参数**任意**都行 |
| `any(InterestRateConfig.class)` | 任意一个 `InterestRateConfig` 对象 |
| `isNull()` | 参数必须是 **null**（新建时没有 excludeId） |

组合示例：

```java
when(interestRateConfigMapper.countOverlap(eq(LEGAL_ENTITY_A), any(), any(), isNull())).thenReturn(0);
```

表示：机构=1001、日期任意、排除 id=null 时，重叠条数返回 0。

---

## 4. Mockito：`verify` ——「有没有按预期调用过」

```java
verify(interestRateConfigMapper).insert(any(InterestRateConfig.class));
```

含义：测试结束后检查——**是否调用过** `insert`？没调用则失败。

```java
verify(interestRateConfigMapper, never()).insert(any());
```

`never()`：在 T3 重叠失败场景里，**断言不应该**执行 `insert`（业务应在 insert 前就抛异常）。

## 5. `ArgumentCaptor` ——「抓住传进去的参数细看」

```java
ArgumentCaptor<InterestRateConfig> captor = ArgumentCaptor.forClass(InterestRateConfig.class);
verify(interestRateConfigMapper).insert(captor.capture());
InterestRateConfig saved = captor.getValue();
assertEquals(LEGAL_ENTITY_A, saved.getLegalEntityId());
```

流程：

1. `verify(...).insert(captor.capture())`：记录这次 `insert` 收到的对象  
2. `captor.getValue()`：取出这个对象  
3. 再断言字段是否正确  

因为 `insert` 是 Mock，不会真写库，所以用 captor **看 Service 组装出来的 entity 对不对**。

## 6. JUnit 断言：`assertXxx` ——「结果必须满足条件」

| 方法 | 含义 | 示例 |
|------|------|------|
| `assertNotNull(x)` | x 不能为 null | `assertNotNull(result.getData())` → 必须有返回 id |
| `assertEquals(expected, actual)` | 两个值必须相等 | `assertEquals(1001L, saved.getLegalEntityId())` |
| `assertTrue(condition)` | 条件必须为 true | `assertTrue(ex.getMessage().contains("Overlapping..."))` |
| `assertFalse(condition)` | 条件必须为 false | `assertFalse(saved.getInactiveFlag())` → 未删除 |

失败时 JUnit 会报：**期望值 vs 实际值**，便于定位。

## 7. 异常测试怎么读

```java
@Test(expected = BizException.class)
public void addOrUpdate_create_overlap_fail() {
    ...
    when(interestRateConfigMapper.countOverlap(...)).thenReturn(1);  // 假装有重叠

    try {
        service.addOrUpdate(req);
    } catch (BizException ex) {
        assertTrue(ex.getMessage().contains("Overlapping rate configurations..."));
        verify(interestRateConfigMapper, never()).insert(any());
        throw ex;  // 再抛出，让 @Test(expected=...) 也通过
    }
}
```

读法：

1. Mock 重叠条数 = 1  
2. 调用 `addOrUpdate` 应抛 `BizException`  
3. 且不应调用 `insert`  

`@Test(expected = BizException.class)` 表示：**不抛这个异常 = 测试失败**。

## 8. Controller 测试里多出来的东西

### `MockMvc` —— 不启动服务器，模拟 HTTP

```java
mockMvc = MockMvcBuilders.standaloneSetup(controller).build();

mockMvc.perform(get(BASE + "list")
        .param("legalEntityId", "1001")
        .accept(MediaType.APPLICATION_JSON))
    .andExpect(status().isOk())                              // HTTP 200
    .andExpect(jsonPath("$.code").value(1))                  // JSON 里 code=1
    .andExpect(jsonPath("$.content[0].id").value(1));        // 第一条 id=1
```

| 部分 | 作用 |
|------|------|
| `mockMvc.perform(get(...))` | 模拟发 GET 请求 |
| `.param("legalEntityId", "1001")` | 查询参数 |
| `.andExpect(status().isOk())` | 期望 HTTP 状态 200 |
| `.andExpect(jsonPath("$.code").value(1))` | 期望 JSON 某字段等于某值 |

这里 `interestRateConfigService` 仍是 `@Mock`，所以 **Controller 真跑，Service 是假的**——只测「接口层参数、返回格式」，不测业务逻辑。

### `ObjectMapper`

把 Java 对象转成 JSON 字符串，用于 `POST` 请求体：

```java
.content(objectMapper.writeValueAsString(req))
```

## 10. 阅读顺序建议（手把手）

拿到一个 `@Test` 方法，按这个顺序读：

1. **方法名**  
   `addOrUpdate_create_success` → 新建应成功  
   `addOrUpdate_create_overlap_fail` → 重叠应失败  

2. **Arrange（when / mockXxx）**  
   Mock 返回什么？模拟什么环境？  

3. **Act（一行核心调用）**  
   `service.addOrUpdate(req)` 或 `mockMvc.perform(...)`  

4. **Assert（assert / verify）**  
   - 返回值对不对？  
   - 该调的方法调了吗？  
   - 不该调的方法没调吗？  
   - 传给 Mapper 的参数对不对？

## 11. 对照表：常见符号一眼懂

```
@Mock          →  替身演员（Mapper/Service）
@InjectMocks   →  主角（被测的 Service/Controller）
when(...).thenReturn(...)  →  替身被问到时怎么答
verify(...)    →  检查替身有没有被叫到
never()        →  检查「绝不能被叫到」
assertEquals   →  两个值必须一样
assertNotNull  →  不能是 null
ArgumentCaptor →  把调用参数抓出来检查
MockMvc        →  假装浏览器发 HTTP
jsonPath       →  检查返回 JSON 的某个字段
```

## 12. 和真实运行的关系（再强调一次）

```
when(mapper.insert(...)).thenReturn(1);
```

这不是「插入成功」，而是：**「假如代码调了 insert，Mock 就假装返回 1，不会执行 SQL」**。

真正验证的是：

- Service 在「无重叠」时会不会走到 `insert`  
- 传给 `insert` 的对象字段对不对  
- 「有重叠」时会不会抛异常且**不**调用 `insert`
