# HME 项目知识库 · 操作规则

> 适用于 `金仕达公司业务类/HME项目文档/` 下的所有文档维护
> 工具链：Obsidian + Claude Code（agent-first 设计）

---

## 核心原则

1. **Agent-first**：知识库的首要读者是 AI agent，文档结构必须让 agent 能快速定位、判断新旧、建立全局认知
2. **三层架构**：`wiki/`（知识导航层）→ 详细文档层（代码/需求/通用/错误分析）→ `shturl.md`（变更追踪层）
3. **术语表是语义锚点**：`通用文档/CTRM业务术语表/` 是所有术语的权威来源
4. **代码文档保留调用链深度**：不简化、不丢失源码行号和类名引用
5. **增量维护**：每次操作只改必要的部分，不做无关重构

## 1. Agent 读取策略

> **本节是 agent 操作的第一步，任何任务开始前必须先执行此流程。**

### 1.1 首次进入知识库

```
Step 1: 读取 wiki/_MAP.md        → 建立全局认知，知道有哪些领域、哪些文档
Step 2: 读取 shturl.md 最近 20 行 → 知道最近变更了什么，哪些知识是新的
Step 3: 根据任务需要，读取对应的 wiki/<领域>.md → 了解该领域的概念和文档索引
Step 4: 按需深入读取详细文档
```

### 1.2 后续访问

```
Step 1: 读取 shturl.md 最近 20 行 → 判断上次访问后有无变更
Step 2: 如有变更且与任务相关，读取变更涉及的文档
Step 3: 如无变更或变更无关，直接读取任务相关的 wiki/<领域>.md 定位文档
Step 4: 按需深入读取详细文档
```

### 1.3 判断知识新旧

- `shturl.md` 中的日期 + 文档路径 = 该文档的最后修改时间
- 每个文档的 `version` 字段 + `date` 字段 = 判断是否需要重新读取
- 如果 agent 缓存中的文档日期 < shturl 中该文档的最新日期 → 文档已更新，需重新读取

## 2. Wiki 知识导航层

> wiki/ 是知识库的"目录+摘要"层，让 agent 不用读完所有详细文档就能建立全局认知。

每个领域一篇，是 agent 进入该领域的入口。

**结构要求：**

```markdown

<!-- 该领域最重要的 3-8 个概念，每个用 1-2 句话解释并链接到详细文档 -->

| 概念 | 说明 | 详细文档 |
|---|---|---|
| <概念名> | <一句话解释> | [[详细文档名]] |

<!-- 该领域的主要业务流程，用 Mermaid 或文字描述 -->

## 关键代码入口

| 入口类/方法 | 功能 | 详细文档 |
|---|---|---|
| <类名>#<方法名> | <做什么> | [[代码文档名]] |

## 涉及的数据库表

| 表名 | 用途 | 详细文档 |
|---|---|---|
| <表名> | <用途> | [[HME数据库#<段落>]] |

## 相关领域

- [[wiki/<其他领域>]] — <关系说明>
```

### 2.3 Wiki 维护规则

- 每次摄入新文档后，检查是否需要更新对应的 `wiki/<领域>.md` 和 `wiki/_MAP.md`
- 领域概览只放**摘要和索引**，不放详细逻辑 — 详细内容在详细文档层
- 如果新文档涉及新领域，创建新的 `wiki/<领域>.md` 并更新 `_MAP.md`
- `_MAP.md` 的"最近更新"列取该领域下所有文档的最新 `date`

## 3. Shturl 变更追踪

> `shturl.md` 是 append-only 的变更日志，agent 用它判断哪些知识是新的。

### 3.1 格式

```markdown
# Shturl — 知识库变更日志

<!-- 最新记录在最上面，agent 从顶部读取 -->

## 2026-06-18
- [摄入] [[定价明细MovementPrice生成逻辑文档]] — 新增 MovementPrice 的完整生成链路分析
- [更新] [[计价公式-pricing-formula-developer-guide]] — 补充了组合计价的 JSON 参数说明
- [wiki] [[wiki/作价与定价]] — 新增"组合计价"概念和关联文档
```

### 3.2 记录类型

| 标签 | 含义 | 何时记录 |
|---|---|---|
| `[摄入]` | 新增了一篇文档 | 摄入流程完成时 |
| `[更新]` | 已有文档被修改 | 文档内容发生实质性变更时 |
| `[wiki]` | wiki 导航层变更 | 新建/更新 wiki 概览文档时 |
| `[关联]` | 文档间建立了新链接 | 发现新的跨文档关系时 |
| `[矛盾]` | 发现知识矛盾 | 新旧信息冲突时 |
| `[缺口]` | 发现知识缺口 | 发现尚未覆盖的重要概念时 |

### 3.3 写入规则

- **只追加，不修改**历史记录
- 最新记录在**最上面**（紧跟标题之后）
- 每条记录必须包含：`[标签]` + `[[文档路径]]` + `— 一句话说明`
- 同一天多次操作合并到同一个日期标题下
- 不需要记录琐碎操作（如修 typo），只记录有知识价值的变更

## 4. 摄入（Ingest）流程

当给我一份新资料时，按以下步骤执行：

### 4.1 阅读与分类

1. 阅读完整原始资料
2. 识别文档类型，决定存放位置：

| 文档类型 | 存放目录 | 命名规则 |
|---|---|---|
| 代码调用链/数据流分析 | `代码文档/<业务模块>/` | `<类名或方法名>-分析说明.md` |
| 需求/功能说明 | `需求文档/<功能名>/` | `<功能名>-<文档角色>.md` |
| Bug/问题排查 | `错误分析-问题排查记录/` | `<问题关键词>-<简要描述>.md` |
| 领域知识/基础概念 | `通用文档/` | 按主题归入已有子目录或新建 |

### 4.2 生成文档

3. 按第 7 节的**文档模板**生成文档内容
4. 填写 frontmatter（见第 6 节）
5. 正文中对首次出现的业务术语添加 `[[wikilink]]`

### 4.3 建立关联

6. 在 frontmatter 的 `related` 字段中关联相关文档
7. 在已有相关文档中补充反向链接

### 4.4 更新导航层

8. 更新对应的 `wiki/<领域>.md`：在概念表、代码入口表或数据库表中追加条目
9. 更新 `wiki/_MAP.md`：更新该领域的"详细文档数"和"最近更新"
10. 如果涉及新领域，创建新的 `wiki/<领域>.md`

### 4.5 记录变更

11. 在 `shturl.md` 顶部追加摄入记录

## 5. 查询（Query）流程

当提问时：

1. **先读 `wiki/_MAP.md`**，确定问题涉及哪些领域
2. **读 `shturl.md` 最近 20 行**，确认相关知识是否有近期更新
3. **读对应的 `wiki/<领域>.md`**，定位具体的详细文档
4. **读取详细文档**，综合信息生成答案
5. 答案中标注信息来源（`📄 [[文档名]]` 格式）
6. 如果涉及业务术语，引用 `[[CTRM业务术语表]]` 中的定义
7. 如果本次问答产生了新的分析结论，询问是否归档为新文档

## 6. Frontmatter 规范

> `tags` 和 `aliases` 是 Obsidian 内置字段，其余为自定义字段。
> `version` 字段用于 agent 判断文档是否需要重新读取。

### 6.1 代码文档

```yaml
---
tags:
  - 代码文档
aliases:
  - "<文档简称>"
module: 物资明细
source_class: ReceiptDeliveryDetailsServiceImpl
source_method: generateDetailsByDocuments
related_tables:
  - receipt_delivery_details
  - movement_price
related:
  - "[[定价明细MovementPrice生成逻辑文档]]"
version: 2                        # 每次实质性修改 +1，agent 据此判断新旧
date: 2026-06-12
---
```

### 6.2 需求文档

```yaml
---
tags:
  - 需求文档
aliases:
  - "<功能简称>"
feature: 升贴水优化
status: 开发中                    # 草稿 / 开发中 / 已完成 / 已上线
role: 后端开发任务
related:
  - "[[相关代码文档]]"
version: 1
date: 2026-06-11
---
```

### 6.3 错误分析

```yaml
---
tags:
  - 错误分析
aliases:
  - "<问题简称>"
severity: 高                      # 高 / 中 / 低
status: 已解决                    # 排查中 / 已解决 / 待跟进
root_cause: 行锁顺序不一致导致死锁
related_tables:
  - cashflow_model_values
related:
  - "[[相关代码文档]]"
version: 1
date: 2026-03-18
---
```

### 6.4 通用文档

```yaml
---
tags:
  - 通用文档
aliases:
  - "<文档简称>"
category: 术语表                  # 术语表 / 基础知识 / 架构说明
related:
  - "[[相关文档]]"
version: 1
date: 2026-06-02
---
```

### 6.5 Wiki 概览文档

```yaml
---
tags:
  - wiki
domain: 作价与定价               # 对应的业务领域
doc_count: 5                     # 该领域下的详细文档数量
last_updated: 2026-06-18         # 该领域最新的文档日期
---
```

### 字段说明

| 字段 | 说明 | Agent 用途 | 是否必填 |
|---|---|---|---|
| `tags` | 文档类型标签 | 按类型过滤 | ✅ |
| `aliases` | 文档别名 | 搜索定位 | 推荐 |
| `version` | 文档版本号 | **判断缓存是否过期**：shturl 日期 + version 双重校验 | ✅ |
| `module` | 业务模块名 | 按模块定位 | 代码文档必填 |
| `source_class` / `source_method` | 核心类/方法名 | 按代码入口定位 | 推荐 |
| `related_tables` | 涉及的数据库表 | 按表定位 | 推荐 |
| `related` | 相关文档列表 | 图谱导航 | ✅（至少1个） |
| `feature` | 需求功能名 | 按功能定位 | 需求文档必填 |
| `status` | 状态 | 按状态过滤 | 需求/错误分析必填 |
| `severity` | 严重程度 | 优先级排序 | 错误分析必填 |
| `root_cause` | 一句话根因 | 快速了解 | 错误分析推荐 |
| `category` | 通用文档子类 | 分类定位 | 通用文档推荐 |
| `domain` | 业务领域 | wiki 导航层标识 | wiki 文档必填 |
| `doc_count` | 领域文档数 | agent 评估领域深度 | wiki 文档必填 |
| `last_updated` | 领域最新日期 | agent 判断领域活跃度 | wiki 文档必填 |
| `date` | 创建/更新日期 | 时间排序 | ✅ |

## 8. 交叉引用规则

### 8.1 必须建立链接的场景

- 代码文档中提到**数据库表名** → 链接到 `[[HME数据库]]` 中对应的表说明段落
- 代码文档中提到**业务术语**（点价、升贴水、日结等） → 链接到 `[[CTRM业务术语表]]`
- 代码文档之间存在**调用关系** → 双向 `related`
- 需求文档涉及**已有代码模块** → 链接到对应的代码文档
- 错误分析的**根因指向某段代码** → 链接到对应的代码文档
- 新文档被摄入后 → 对应的 `wiki/<领域>.md` 中追加链接

### 8.2 链接格式

- 正文中：`[[文档名]]` 或 `[[文档名|显示文本]]`
- frontmatter 中：`related` 字段（wikilink 列表）
- 跨模块引用时加简要说明：`定价逻辑参见 [[定价明细MovementPrice生成逻辑文档|MovementPrice 生成逻辑]]`

## 9. 维护（Lint）流程

触发健康检查时：

### 9.1 导航层一致性

- [ ] `wiki/_MAP.md` 的领域列表是否覆盖了所有 `wiki/<领域>.md`
- [ ] 每个 `wiki/<领域>.md` 中列出的详细文档是否真实存在
- [ ] `wiki/<领域>.md` 的 `doc_count` 是否与实际文档数一致
- [ ] `_MAP.md` 的"最近更新"日期是否与各领域的最新 `date` 一致

### 9.2 Frontmatter 完整性

- [ ] 所有文档是否都有 `tags` 和 `version`
- [ ] 代码文档是否填了 `module`
- [ ] 需求文档和错误分析是否填了 `status`
- [ ] `related` 字段是否有至少一个链接

### 9.3 链接健康

- [ ] `related` 链接是否双向
- [ ] 是否有断链
